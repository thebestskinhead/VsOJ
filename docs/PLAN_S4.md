## 0. 范围

### 0.1 本轮要做（运行期）

| # | 能力 | 触发源 | 优先级 |
|---|---|---|---|
| A | 重访自动刷新 | 用户重新打开题目页，且缓存超 15 分钟、网络可用 | 高 |
| B | 单题强制刷新 | 题目页内按钮 / 题目列表项右键菜单 | 高（高频） |
| C | 全量强制刷新 | 侧边栏「题目」标题栏按钮 | 中 |
| D | 过期可见性 | 题目页常驻「更新于 X 分钟前」 | 高 |

### 0.2 本轮不做

- **S5 进入比赛自动初始化**：与运行期刷新**语义解耦**。二者只是碰巧都写缓存：
  - 初始化 = 阶段性的、一次性的、可重入的"建立工作区"动作；
  - 运行期刷新 = 每次访问都可能发生的"保持数据新鲜"动作。
  - 本轮**不引入任何"进入比赛即触发"的代码路径**，只提供被调用的能力。
- S6 MCP 扩展、S7 状态页静态化、S3 静态资源外置。

## 2. 前置修正：推翻两个我此前写错的结论

上一轮 `PROGRESS.md` 里「三个缺口」的表述有误，实测数据如下。

### 2.1 「多样例缺失」不成立

扫描 `cid=3772` 与 `cid=3775` 共 40 个 `pid` 位置（其中 24 个是有效题目页）：

- **24/24 都是单组样例**，结构固定为 `<pre class=content><span id="sampleinput" class=sampledata>…` 与 `id='sampleoutput'`；
- 不存在多组样例的页面。

→ 缓存布局支持 `1.in/2.in/…` 仍保留（前瞻性），但**本轮不需要多样例解析**，落盘直接写 `1.in` / `1.out`。

### 2.2 「图片抓不到」不成立，真实缺口是"没落盘"

- 题面图片形态：`<img src="/JudgeOnline/upload/image/20170611/20170611222431_16939.png" alt="" />`，**是相对路径**；
- 现有 `ProblemService.inlineImages()` 的正则 `/<img\s+[^>]*src=["'](\/[^"']+)["'][^>]*>/gi` **能正常命中**；
- 且调用点只作用于 `description` / `inputDesc` / `outputDesc` 三个字段，**页脚脚本里的二维码不会被误抓**（实测该脚本内 4 个 `<img>` 全在 `<script>` 中且为绝对 URL）；
- 站点对 `/JudgeOnline/...` 与去前缀的 `/upload/...` 都能解析：实测均返回 `HTTP 200 / image/png / 24753 bytes`。

→ 结论：**图片链路是有效的**，缺的只是"已抓到的 Buffer 没有落盘、也没有结构化字段暴露给 MCP"。

### 2.3 题面带图的真实频率：约 4%

- 24 个有效题目页中，**仅 1 道**（`cid=3775&pid=16`）题面含图片。
- → 图片能力要做，但**优先级低于刷新与离线预览**，放在后续项（§8）。

### 2.4 顺带发现的新缺口

- **「提示」小节被丢弃**：24 道有效题中有 4 道含「提示」小节（`<h4>提示</h4>`），而 `ProblemDetail` 没有对应字段。

## 4. 关键设计

### 4.1 两级 TTL 的分工（C1）

| 配置 | 默认 | 语义 | 用在 |
|---|---|---|---|
| `oj.cache.ttlSeconds` | 180 | **同步读**：命中且新鲜就直接用，**不发起任何请求** | 轻量列表（比赛列表、题目列表） |
| `oj.cache.staleSeconds` | 900 | **异步刷**：先渲染缓存，超过该年龄才在**后台**刷新 | 题目详情（本轮） |

两者**不冲突**：题目详情页走"渲染缓存 + stale 后才后台刷"，不使用 `ttlSeconds`；列表类走 `ttlSeconds`。文档需明确写出这条分工，避免后续混淆。

`oj.cache.offline = true` 时，两者都跳过网络，直接吃缓存。

### 4.2 网络可达性探测

- 端点：`GET /csrf.php`。理由：85 B 最小、无副作用，且顺带刷新服务端会话 mtime（对 S2 的保活有正向作用）。
- 超时 4s，`validateStatus: () => true` —— **只要能拿到 HTTP 响应就算可达**，不区分状态码。
- **结果缓存 30s**：避免用户连点几个题目时重复探测。
- 与 `session/guard.ts` 的分工：guard 判定"这次失败是什么性质"，connectivity 只回答"现在能不能上网"。**不要**用 `AuthService.isLoggedIn()` 代替——那是登录判定。

### 4.3 重访刷新的执行顺序（能力 A）

```
打开题目页
 ├─ 1. 读缓存（allowStale）→ 命中则立即渲染，信息栏显示「更新于 X 分钟前」
 ├─ 2. 未命中 → 走网络（原路径），成功后写缓存 + 更新信息栏为「刚刚」
 ├─ 3. 命中但 offline            → 结束（信息栏「离线预览 · 缓存于 X 分钟前」）
 ├─ 4. 命中且 age < staleSeconds → 结束（零请求）
 ├─ 5. 命中且 age ≥ staleSeconds → 探测网络
 │       ├─ 不可达 → 结束（静默，遵守 C8）
 │       └─ 可达 → 后台 fetch → 写缓存
 │                 ├─ 内容有变化 → postMessage 增量替换（保留 scrollTop）
 │                 └─ 内容无变化 → 只更新时间戳
 └─ 6. 后台 fetch 失败 → 静默（被动场景，遵守 C8）
```

要件：
- 首屏**不阻塞**在网络上（这是"离线预览"的核心）；
- 决策逻辑全在 `revalidate.ts`，通过注入 `readCached / statCached / isReachable / fetchAndStore / isOffline` 实现，**可脱 VS Code 单测**（延续 S2 `KeeperDeps` 的做法）。

### 4.4 过期可见性（C9）

题目页顶部常驻一条信息栏，状态机：

| 场景 | 文案 |
|---|---|
| 在线，缓存新鲜 | `本地缓存 · 更新于 3 分钟前` |
| 在线，已过期，正在后台刷新 | `本地缓存 · 更新于 22 分钟前` + `正在更新…` |
| 在线，刷新完成 | `已更新 · 刚刚` |
| 离线模式 / 无网 | `离线预览 · 缓存于 22 分钟前` |
| 无缓存且不可达 | `无法获取题目内容（网络不可用，且本地无缓存）` |

- **时间基准 = 缓存文件 mtime**，即"上次成功从网络同步的时间"。刷新失败不写盘 → 时间不变，语义正确。
- 右侧带刷新按钮（C3①），点击即 C4 的强制刷新。

### 4.5 单题强制刷新（能力 B，C3/C4/C10）

- 命令：`oj.cache.refreshProblem`（参数：`cid`、`pid`；无参数时取 `state` 当前上下文）。
- 入口只暴露两个：题目页内按钮、题目列表项右键菜单。
- 无视 15 分钟阈值，**不弹确认**，直接拉取并覆盖缓存。
- 失败**必须报错**（C10）：`showErrorMessage` 带上失败原因分类（复用 `session/guard.ts` 的 `FailureKind`）。
- 成功后在题目页内原地刷新内容与时间戳，不重开面板。

### 4.6 全量强制刷新（能力 C，C5/C6/C7）

命令 `oj.cache.refreshAllProblems`，菜单位置 `view/title`，`when: view == oj.problems && oj.inContest && !oj.offline`。

执行步骤（严格串行）：
1. 前置检查：`cid` 存在 → 非 offline → `isReachable()`。任一不满足，提示并**中止**。
2. `showWarningMessage('将刷新「<比赛名>」全部 N 道题的缓存（题目列表 + 题目详情 + 提交状态），继续？', { modal: true }, '继续')`。
3. `withProgress({ location: Notification, cancellable: true })`：
   - 先拉题目列表 → 写 `problems.json`
   - 逐题（i/N）：拉详情 → 写 `problem.json` + `problem.md`
   - 最后拉状态 → 写 `status.json`
4. 结果：完成数 / 失败数汇总；失败题号一并列出，可点击查看（写入 Output 通道）。
5. 取消：已完成的保留，**不回滚**（缓存层面无一致性要求）。

要点：
- 进度文案必须显示 `i/N` 与当前题号，否则几十道题像卡死；
- 串行间隔不做人为 sleep（C7 已够友好），但**失败不自动重试**，避免放大站点压力。

## 7. 风险与不变更承诺

| 风险 | 应对 |
|---|---|
| **行为变化：题目页从"每次实时拉"变为"缓存优先"** | 这是 C2/D 的必然结果。首屏会先显示缓存再后台更新。需在 README 明确写出，并保证 `oj.cache.enabled = false` 时**完全退回旧行为**（实时拉取、不读不写缓存） |
| 默认值减少网络请求可能让用户误以为"不更新" | 信息栏常驻「更新于 X 分钟前」（C9）即是补偿；同时 B 提供随时强刷的出口 |
| 全量刷新请求量 | 串行 + 无重试 + 可取消；确认框明示题目数 |
| `csrf.php` 探测被当作"保活" | 属正向副作用；但探测**不得**作为登录态判据，二者职责在代码注释中写死 |
| 信息栏被 CSP 拦截 | 本轮仍在 TS 内拼 HTML（S3 未做）；不使用内联 `<script>`，按钮走 `postMessage` |

不变更：不改 `parser.ts` 解析口径、不改 `client.ts` cookie 策略、不引入并发库、不新增 HTTP 客户端。
